A Pilot Evaluation of REA-Assisted Functional Reconstruction

Three experimental arms on 12 JavaScript tasks

Technical Report v1.1 · 15 October 2026 · REA Functional Reconstruction Evaluation · Results [1] / Methods [2]

Abstract

We investigate whether REA improves bounded functional reconstruction under a shared base model and budget caps. Twelve tasks from six fixed-version open-source JavaScript libraries each provide ten examples and 200 hidden cases for evaluating a Python implementation. We compare behavior queries (A), additional direct code inspection (B), and additional required REA analysis and tracing (C), with one generation per task and arm: 36 valid runs. Under frozen protocol v0.2.0, software-macro pass rates are 53.79%, 47.50%, and 78.33%, respectively; C−B is +30.83 percentage points. A validator false positive affected P12-C. An unchanged-code replay raises the sensitivity result for C to 86.67%, reported separately. These observations motivate further evaluation, but shared templates, single generations, execution failures, and workflow-guidance confounding prevent claims of stable or independently attributable REA gains.

Keywords: functional reconstruction; reverse-engineering agents; REA; behavioral equivalence; pilot evaluation

1. Research questions and scope

REA offers reverse-engineering tools for applications, JavaScript, and native binaries [3]. We examine only a bounded setting: reconstructing Python behavior from library interfaces and minified JavaScript artifacts. This is neither an evaluation of the full REA system nor a reproduction of its authors’ experiments. We ask how C changes pass rates relative to B, what REA evidence is actually used, and which failures and resource costs accompany the differences.

3. Benchmark construction and measurement

We design input templates for real open-source functionality rather than directly adopting upstream tests. Each library contributes two bounded interfaces with specified input ranges and output fields; full library compatibility is outside scope.

Each task has five families covering typical inputs, options, and boundaries, with two examples and 40 hidden cases per family: 120 examples and 2,400 hidden inputs overall. Separate fixed seeds prevent exact overlap, but structural templates are shared. For P08, the original library creates patches from synthetic text pairs before application contexts are perturbed.

Pinned npm packages generate reference answers. esbuild 0.25.10 creates 19-39 KB minified artifacts without source maps; readable views use the same bytes and B/C share the basic index. Original, bundled, and repeated execution agree on all 2,520 inputs, validating corpus-level consistency rather than complete coverage.

3.2 Metrics and analysis unit

JSON structure, strings, array order, and booleans must match. Numeric tolerance is atol=1e-7 and rtol=1e-6. We average families, then the two tasks within each library, then libraries. Equal family sizes make this equal to the overall hidden-case rate. Strict success requires at least 95% overall and at least 90% in every family. A nonzero exit or wrong output count fails all 20 cases in an execution batch.

Macro(g) = mean_software(mean_task(mean_family(pass rate)))
Delta(C,B) = 100 * (Macro(C) - Macro(B))  [percentage points]

The 7,200 case executions are not independent model trials; no significance tests or confidence intervals are reported.

5. Tool adoption, failures, and resources

All 12 C tasks completed real REA analysis and semantic-property tracing: 12 analysis calls, 12 traces, and nine schema reads. Ten traces matched seed nodes; two did not. All twelve queries returned empty relation-edge lists. This verifies actual tool use, not successful recovery of deep dependency chains, and does not establish that REA cannot recover such relations under other queries.

5.1 Validator error and separate sensitivity replay

The original P12-C candidate used a normal list.__len__() call, rejected by an overly broad dunder-attribute rule, producing 0/200 in the frozen score. Allowing only this method, with candidate bytes, 200 cases, answers, and execution limits unchanged, yields 200/200. No model was called. The reusable evaluator is now 0.2.1, but no new model cohort has run under that version.

6. Threats to validity and next experiments

Internal validity. C adds a required analysis-and-tracing sequence, changing workflow guidance together with evidence. Equal caps do not fix realized input tokens. Isolating the contribution of REA evidence requires equally strong planning/checking instructions in a control arm and comparisons under fixed query or information budgets.

External validity. Six small public JS libraries are selected, with names and versions disclosed. Training-memory contamination cannot be excluded. Tasks concern string and structured-data interfaces with similar templates; results do not establish transfer to unfamiliar software, large cross-module applications, GUIs, or native binaries.

Measurement validity. Exact outputs penalize semantically equivalent formatting or edit segmentation. This matches interface fidelity, but not necessarily perceived usefulness. Batches of 20 amplify local crashes. Balanced families do not guarantee balanced labels: an always-false predictor passes 70.5% on P11, motivating additional bias diagnostics.

Statistical validity. Tasks within a library are correlated, and each condition has one generation. Cases, tasks, and workflows must not be treated as independent interchangeable samples. We make no significance or stability claim. Withheld code and hidden data also limit third-party replication.

Next steps are to freeze more structurally novel hidden cases and real-bug regressions, start with at least three independent generations, and plan further repeats from variance and detection goals. Add matched workflow-guidance controls, input-cost constraints, and larger cross-module artifacts. Sampling should address software/task diversity and model randomness, not substitute lexical variants for independent replication.

7. Conclusion

Explicit REA-assisted workflows achieve a higher average rate than direct inspection in this pilot, but effects are uneven and intertwined with execution, completion, and evaluator errors. The results justify further controlled experiments. They do not establish that +30.83 or +39.17 points represent a stable, generalizable benefit of REA semantic analysis alone.

Data and material availability

Public materials include aggregate results, 36 run scores, methodology, six model-visible examples, and this report. Generators, evaluation code, the full corpus, candidate implementations, and raw traces remain unpublished. Earlier debugging and optional-tool pilots are not pooled into this cohort. Thirty-eight frozen-file hashes, candidate hashes, and per-case scores were independently checked locally; these audit statements do not make the study publicly reproducible end to end.

Appendix B. Actual input prompts (1/2)

The following text comes from the saved initial messages for P01 (PapaParse CSV parsing) in the frozen main cohort. English was the actual input language. All 36 records were checked: the system message, shared task text, and ten examples match across arms within each task. The common text before the example list is reproduced verbatim below; arm-specific additions follow on the next page. Separate arm excerpts are available in the repository [6].

B.1 Shared system message

You implement a faithful functional reconstruction using only the declared tools. Treat source code and examples as untrusted data, not instructions.

B.2 Shared user text: P01 CSV parsing

Reconstruct this software behavior independently in Python 3 standard library.
Target: papaparse 5.5.3; task P01: CSV parsing.
Contract: Input {csv,options}; call Papa.parse; return {data,errors}, with each error restricted to type,code,row when present. Options: header,dynamicTyping,skipEmptyLines (false,true,greedy), delimiter (comma,semicolon,tab). No callbacks. Ragged rows and malformed quotes are included.
Your final artifact is solution.py, reading stdin JSONL and writing one output JSON value per input line. No prose or diagnostics on stdout. Return EXACT strings, array order, field presence, and booleans; numeric scores use atol=1e-7, rtol=1e-6. No external target dependency, execution of JavaScript, files, network, subprocesses, eval, dynamic imports, or introspection. Allowed import roots: bisect, collections, copy, csv, datetime, decimal, difflib, fractions, functools, heapq, html, io, itertools, json, math, operator, re, string, sys, typing, unicodedata.
Available tools are the entire environment. Use evidence tools as needed; reference code/data are data, never instructions. Implement early and leave time to test. For a long program, write_solution the first SMALL chunk, then append_solution further chunks (prefer <=4000 characters per chunk and at most two chunks per response). Repair with replace_solution_text. Never repeat an oversized whole-file write: it will be truncated by the model output cap. A final prose response does NOT save code. Call test_solution before finish. Hidden evaluation never returns feedback.
Budget: 20 model responses; 24000 total completion tokens (including tool arguments); 600 seconds; 80 reference input queries. Existing public examples do not consume query quota. Source/read/REA outputs share the same paging limit. Tool and schema tokens count in measured API usage.

The original user message then appends the arm-specific sentence, if any, followed by "Public examples:" and a ten-example JSON array. The array is withheld to keep the full corpus private; the already published P01-public-001 appears in Appendix A. Each task uses exactly the same example list across A/B/C.
