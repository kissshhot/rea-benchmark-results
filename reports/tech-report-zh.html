REA 辅助功能重建的先导评测

基于 12 项 JavaScript 任务的三组对照实验

技术报告 v1.0 · 2026-10-15 · REA Functional Reconstruction Evaluation · 数据 [1] / 方法 [2]

摘要

本文评估在相同基础模型和预算上限下，加入 REA 是否改善有限接口的功能重建。我们从 6 个固定版本的开源 JavaScript 库构建 12 个任务，每任务提供 10 条示例，并以 200 条隐藏用例检验候选 Python 程序。三种设置为行为查询（A）、增加代码检查（B）和增加必需的 REA 分析与追踪（C），每任务每组仅生成一次，共 36 次有效运行。冻结协议 v0.2.0 下，软件宏平均通过率分别为 53.79%、47.50% 和 78.33%，C−B 为 +30.83 个百分点。P12-C 存在判分器误拦截；保持原代码与用例不变的独立重放使 C 的敏感性结果变为 86.67%，单独报告。当前证据支持进一步验证，但共享模板、单次生成、程序运行失败以及流程引导混杂，使结果尚不足以证明稳定或可单独归因于 REA 的增益。

关键词：功能重建；逆向工程代理；REA；行为一致性；先导评测

1. 研究问题与范围

REA 项目提供面向应用、JavaScript 和原生二进制的逆向分析工具 [3]。本报告只研究其中一个受限场景：从库接口行为及压缩 JS 工件重建 Python 实现。它不是对 REA 全部能力的评估，也不是作者原有评测的复现。研究问题分别是：C 相对 B 的功能通过率有何变化；模型实际使用了哪些 REA 证据；变化伴随怎样的运行失败和资源消耗。

2. 实验设置代表什么

设置可见信息与强制步骤对照意义
A：行为查询任务契约、库名与版本、10 条示例；可自选输入查询原软件。不能查看目标代码或调用 REA。仅凭行为证据和模型已有知识重建。
B：直接代码检查继承 A 的信息；增加压缩目标、格式化视图、文本搜索和基础函数索引。写代码前须读取目标或函数索引。在 A 上增加代码访问及检查流程。
C：REA 辅助检查继承 B 的代码访问能力；写代码前必须完成 REA 分析及相关属性的语义追踪。在代码基线上增加 REA 证据与显式流程引导。

三组使用同一请求模型 deepseek-v4-flash；服务返回标识为 deepseek-flash，无法独立确认内部权重快照。C−B 是主要工作流比较；B−A 衡量加入代码检查的变化，C−A 衡量组合工作流的变化。三者都不是已经分离混杂因素的因果效应。

3. 任务构建与测量方法

任务来自真实开源功能，输入模板由我们编写，未直接搬用上游仓库单元测试。每个库拆出两个有边界的接口；候选程序只需复现指定输入范围与输出字段，不要求完整兼容该库。

表 1. 六个目标库与十二项任务。

固定版本目标任务 ID功能
PapaParse 5.5.3P01 / P02CSV 解析 / 导出
Fuse.js 7.1.0P03 / P04字符串 / 字段加权搜索
marked 15.0.12P05 / P06行内 / 块级 Markdown
diff-match-patch 1.0.5P07 / P08语义 diff / 模糊补丁
semver 7.7.2P09 / P10版本排序 / 范围筛选

每任务设置五类模板，覆盖普通输入、选项变化与边界行为。每类生成 2 条模型可见示例和 40 条隐藏输入；合计 120 条示例、2,400 条隐藏输入。两部分使用不同固定种子并排除重复输入，但主要共享结构模板。P08 的补丁由原库从合成文本对生成，再改变应用上下文。

标准答案直接来自固定版本 npm 原包。原包被 esbuild 0.25.10 打包压缩，无 source map；格式化视图从相同压缩结果生成，B、C 使用相同基础索引。工件约 19-39 KB。原包、压缩包与重复执行的 2,520 条输出全部一致；这验证本数据上的一致性，不等于完整覆盖。

3.1 统一预算与执行

设置项本轮取值与含义
模型响应最多 20 次；一次响应可含多个工具调用。
输出 token每响应最多 6,144；每工作流累计最多 24,000。
原软件查询最多 80 条自行选择的输入；10 条示例可另行测试。
时间600 秒后停止发起新请求，允许在途请求完成；REA 调用计入。
采样与信息隔离temperature=0.2，thinking=disabled；隐藏测试不反馈给模型。
候选执行Python 标准库、JSONL 接口；离线隔离、CPU/内存/输出限制。

三组都可分段写入、读取、修改代码并运行公开示例。每任务三组并行、调度顺序随机化，任务依次执行。输入 token 没有等量配额，因此相同预算上限不代表相同实际信息量或成本。

3.2 指标与分析单位

JSON 结构、字符串、数组顺序和布尔值须一致；数值容差为 atol=1e-7、rtol=1e-6。主指标依次平均五类用例、同软件的两个任务和六个软件；本轮各类等大，等价于全部隐藏用例平均。严格成功要求任务总通过率至少 95%，且每类至少 90%。每 20 条输入成批执行，非零退出或输出条数错误使该批全部失败。

Macro(g) = mean_software(mean_task(mean_family(pass rate)))
Delta(C,B) = 100 * (Macro(C) - Macro(B))  [percentage points]

每个任务/条件只有一份候选实现。7,200 次隐藏执行是同一套 2,400 条输入在三组上的评测，不是 7,200 个独立模型试验；本文不报告显著性检验或置信区间。

4. 冻结主结果

表 2. 冻结协议 v0.2.0；不混入事后重放。

条件软件宏平均严格成功任务
A53.79%2/12

主要差值 C−B 为 +30.83 个百分点；C−A 为 +24.54 个百分点，B−A 为 −6.29 个百分点。按软件聚合，PapaParse、Fuse.js、marked、minimatch 为正向，semver 持平，diff-match-patch 为负向（−10.0 个百分点）。增益并非所有任务一致出现。

例如 Fuse.js 的加权记录搜索由 B 的 0.5% 提升至 C 的 100%，而模糊补丁任务由 60% 降至 40%。A 的整体通过率高于 B，但严格成功任务更少，说明平均部分完成度与高阈值任务成功衡量不同侧面。B 的较多执行失败也使“提供代码是否有益”不能仅由平均分推断。

5. 工具采用、失败与资源分析

C 组 12/12 任务均完成真实 REA 分析与语义属性追踪，共 12 次分析、12 次追踪及 9 次 schema 查阅。10 次追踪命中种子节点，2 次未命中；这 12 次查询的关系边列表均为空。它们证明工具被实际调用，但不能证明恢复了深层依赖链，也不能据此判定 REA 在其他查询上没有这种能力。

5.1 判分器误拦截与独立敏感性检查

P12-C 原代码调用正常的 list.__len__()，被过宽的双下划线属性规则拒绝，冻结主成绩为 0/200。只放行该方法，保持候选字节、200 条输入、答案与执行限制不变重放后为 200/200。该重放没有新增模型调用；当前评测器 0.2.1 已修正规则，但尚无该版本的新模型批次。

口径C 宏平均C−BC 严格成功
冻结 v0.2.078.33%+30.83 pp6/12
事后敏感性检查86.67%+39.17 pp7/12

因此，冻结结果与敏感性结果应并列披露。前者保留预先记录的评分口径，后者揭示评测器错误的影响；两者都不提供独立重复或稳定性证据。

6. 有效性威胁与后续实验

内部有效性：C 组额外要求“先分析、再追踪”，同时改变了证据和工作流引导；相同预算上限也未固定实际输入 token。要识别 REA 证据的独立贡献，需要加入相同强度的规划与检查对照，并比较固定查询或信息配额下的结果。

外部有效性：仅选择六个小型公开 JS 库，库名和版本公开，无法排除模型训练记忆。任务限定为字符串与结构化数据接口，模板相似；不能外推到陌生软件、跨模块大型应用、GUI 或原生二进制。

测量有效性：精确输出比较会惩罚虽语义等价但格式或分段不同的实现；这符合接口一致性目标，但不等于用户感知可用性。20 条成批执行会放大局部崩溃的影响。类别平衡也不等于标签平衡，P11 全部回答 false 即可通过 70.5%，提示需要补充偏置诊断。

统计有效性：同一库内任务相关，每条件只生成一次。任务、用例和模型工作流不能混为独立样本。当前不提供显著性或稳定性结论；完整代码与隐藏集暂不公开，也限制第三方独立复现。

后续应先冻结更多结构性隐藏用例与真实缺陷回归案例，再至少进行三次独立生成作为起步，并按方差与检测目标规划更充分的重复；加入同强度流程引导对照、输入成本约束和更大跨模块工件。样本量应围绕软件/任务与模型随机性规划，不能用模板变体数量替代。

7. 结论

在本先导集上，显式 REA 辅助工作流相对直接代码检查获得更高平均通过率，但收益不均匀，且与流程执行、提交完整性及判分器问题交织。结果支持进一步受控实验，不支持把 +30.83 或 +39.17 个百分点直接解释成稳定、普适的 REA 语义分析收益。

数据与材料可用性

公开材料包括聚合结果、36 次运行成绩、方法说明、六条模型可见示例及本报告。测试生成器、评测代码、完整测试集、候选实现和原始轨迹暂不公开。早期调试及可选工具试验未并入本主批次。38 个冻结文件哈希、候选代码哈希和逐例判分曾在本地独立复核；这些审计陈述不等于公开可复现。
